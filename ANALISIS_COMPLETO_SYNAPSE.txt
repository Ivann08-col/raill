1. TABLA: USUARIO
================================================================================

DESCRIPCION FUNCIONAL:
Almacena informacion de usuarios del sistema. Cada usuario tiene credenciales unicas, 
perfil personal y datos de acceso. Es la tabla central que se relaciona con practicamente 
todas las demas tablas.

CAMPOS PRINCIPALES:
- id_usuario (STRING UUID, PK): Identificador unico del usuario
- username (STRING 100, UNIQUE): Nombre de usuario para login
- correo (STRING 100, UNIQUE): Email unico del usuario
- password (STRING 255): Contraseña hasheada con werkzeug
- avatar_url (STRING 255, NULLABLE): URL de la foto de perfil
- fecha_registro (DATETIME): Timestamp de cuando se creo la cuenta
- ultimo_acceso (DATETIME, NULLABLE): Timestamp del ultimo login
- rol_id (INTEGER, FK -> rol.id): Rol del usuario (admin/usuario)
- activo (BOOLEAN): Indica si la cuenta esta activa
- nombre_completo (STRING 200, NULLABLE): Nombre completo del usuario
- telefono (STRING 20, NULLABLE): Numero de contacto
- ubicacion (STRING 200, NULLABLE): Localizacion del usuario
- fecha_nacimiento (DATE, NULLABLE): Fecha de nacimiento
- descripcion (TEXT, NULLABLE): Bio o descripcion personal
- preferencias (JSON, NULLABLE): Preferencias del usuario (habitos, ajustes)

RELACIONES CON OTRAS TABLAS:
- usuario -> rol: Muchos a Uno (cada usuario tiene un rol)
- usuario -> tarea: Uno a Muchos (un usuario puede tener muchas tareas)
- usuario -> sesion: Uno a Muchos (un usuario tiene multiples sesiones)
- usuario -> usuario_sala: Uno a Muchos (un usuario puede estar en varias salas)
- usuario -> recompensa_usuario: Uno a Muchos (relacion con recompensas obtenidas)
- usuario -> progreso: Uno a Muchos (registro diario de progreso)
- usuario -> estado_animo: Uno a Muchos (registro de estados de animo)
- usuario -> sala (como creador): Uno a Muchos (usuario crea salas)
- usuario -> mensaje_sala: Uno a Muchos (usuario envia mensajes en salas)
- usuario -> password_reset_code: Uno a Muchos (codigos de recuperacion)

RUTAS BACKEND DISPONIBLES (usuario_routes.py):
- GET /api/usuario (lista todos los usuarios) - JWT requerido
- GET /api/usuario/<usuario_id> (obtiene un usuario especifico) - JWT requerido
- POST /api/usuario (crea nuevo usuario) - JWT requerido
- PUT /api/usuario/<usuario_id> (actualiza usuario) - JWT requerido
- PUT /api/usuario/<usuario_id>/preferencias (actualiza preferencias) - JWT requerido
- DELETE /api/usuario/<usuario_id> (desactiva usuario soft-delete) - JWT requerido

RUTAS AUTH (auth.py):
- POST /api/auth/register (registro de nuevo usuario)
- POST /api/auth/request-password-reset (solicita codigo de recuperacion)
- POST /api/auth/reset-password (restablece contraseña con codigo)

================================================================================

DESCRIPCION FUNCIONAL:

que determina sus permisos en el sistema.

3. TABLA: TAREA
================================================================================

DESCRIPCION FUNCIONAL:
Almacena tareas individuales de usuarios. Cada tarea tiene estado, prioridad, 
fecha de vencimiento y puede estar asociada a una sala grupal. Las tareas pueden 
ser personales o de una sala.

CAMPOS PRINCIPALES:
- id_tarea (STRING UUID, PK): Identificador unico de la tarea
- usuario_id (STRING UUID, FK -> usuario.id_usuario): Dueno de la tarea
- sala_id (STRING UUID, FK -> sala.id_sala, NULLABLE): Sala asociada
- titulo (STRING 200): Titulo descriptivo de la tarea
- descripcion (TEXT, NULLABLE): Descripcion detallada
- fecha_creacion (DATETIME): Cuando se creo la tarea
- completada (BOOLEAN): Si esta marcada como completada
- estado (STRING 20): Estado actual (Pendiente, EnProgreso, EnEspera, Completado)
- fecha_vencimiento (DATE, NULLABLE): Fecha limite para completarla
- prioridad (STRING 20): Nivel de prioridad (baja, media, alta)
- comentario (TEXT, NULLABLE): Comentarios o notas adicionales

RELACIONES CON OTRAS TABLAS:
- tarea -> usuario: Muchos a Uno (varias tareas de un usuario)
- tarea -> sala: Muchos a Uno (tareas pueden ser de una sala)

RUTAS BACKEND (tarea_routes.py):
- GET /api/tarea (lista tareas del usuario actual con filtros)
- GET /api/tarea/<id_tarea> (obtiene tarea especifica)
- POST /api/tarea (crea nueva tarea)
- PUT /api/tarea/<id_tarea> (actualiza tarea)
- DELETE /api/tarea/<id_tarea> (elimina tarea)

PARAMETROS DE FILTRO (GET):
- sala_id: Filtrar por sala
- estado: Filtrar por estado
- prioridad: Filtrar por prioridad

4. TABLA: SALA
================================================================================

DESCRIPCION FUNCIONAL:
Salas de estudio/trabajo colaborativo. Las salas pueden ser publicas o privadas 
(con codigo de acceso). Un usuario crea la sala y otros se unen a ella. Las salas 
contienen participantes, sesiones grupales y mensajes.

CAMPOS PRINCIPALES:
- id_sala (STRING UUID, PK): Identificador unico de la sala
- nombre (STRING 100): Nombre de la sala
- descripcion (TEXT, NULLABLE): Descripcion de la sala
- fecha_creacion (DATETIME): Cuando se creo la sala
- creador_id (STRING UUID, FK -> usuario.id_usuario): Usuario que la creo
- max_participantes (INTEGER, NULLABLE): Limite de participantes
- es_privada (BOOLEAN): Si requiere codigo de acceso
- codigo_acceso (STRING 6, NULLABLE): Codigo para salas privadas
- estado (STRING 20): Estado de la sala (activa, pausada, cerrada)

RELACIONES CON OTRAS TABLAS:
- sala -> usuario (creador): Muchos a Uno
- sala -> usuario_sala: Uno a Muchos (participantes de la sala)
- sala -> sala_sesion: Uno a Muchos (sesiones grupales)
- sala -> tarea: Uno a Muchos (tareas de la sala)
- sala -> mensaje_sala: Uno a Muchos (mensajes en la sala)

RUTAS BACKEND (sala_routes.py):
- GET /api/sala (salas donde el usuario es miembro activo)
- GET /api/sala/publicas (todas las salas publicas)
- GET /api/sala/<sala_id> (detalles de una sala con participantes)
- POST /api/sala (crear nueva sala)
- PUT /api/sala/<sala_id>/actualizar (actualizar datos de la sala)
- POST /api/sala/<sala_id>/unirse (unirse a una sala publica)
- POST /api/sala/<sala_id>/unirse-privada (unirse con codigo)
- POST /api/sala/<sala_id>/salir (salir de una sala)

5. TABLA: SESION
================================================================================

DESCRIPCION FUNCIONAL:
Registra sesiones de meditacion/estudio individual o grupal. Cada sesion tiene 
una tecnica asociada, duracion real, fecha de inicio/fin y estado. Permite rastrear 
el tiempo dedicado a cada tecnica de concentracion.

CAMPOS PRINCIPALES:
- id_sesion (STRING UUID, PK): Identificador unico
- usuario_id (STRING UUID, FK -> usuario.id_usuario): Usuario que realizo la sesion
- tecnica_id (STRING UUID, FK -> tecnica.id_tecnica): Tecnica utilizada
- fecha_inicio (DATETIME): Cuando comenzo la sesion
- fecha_fin (DATETIME, NULLABLE): Cuando termino la sesion
- duracion_real (INTEGER, NULLABLE): Duracion en segundos/minutos que duro realmente
- estado (STRING 20): Estado (Pendiente, EnProgreso, Completado, Cancelado)
- es_grupal (BOOLEAN): Si fue una sesion grupal

RELACIONES CON OTRAS TABLAS:
- sesion -> usuario: Muchos a Uno
- sesion -> tecnica: Muchos a Uno
- sesion -> sala_sesion: Uno a Muchos (relacion con salas)
- sesion -> sesion_tecnica_param: Uno a Muchos (parametros especificos)

RUTAS BACKEND (sesion_routes.py):
- GET /api/sesion (lista sesiones del usuario con filtros)
- GET /api/sesion/<sesion_id> (obtiene sesion especifica)
- POST /api/sesion (crea nueva sesion)
- PUT /api/sesion/<sesion_id> (actualiza sesion)
- DELETE /api/sesion/<sesion_id> (elimina sesion)

PARAMETROS DE FILTRO (GET):
- tecnica_id: Filtrar por tecnica
- estado: Filtrar por estado
- es_grupal: true/false
- fecha_inicio: Desde esta fecha
- fecha_fin: Hasta esta fecha

7. TABLA: RECOMPENSA
================================================================================

DESCRIPCION FUNCIONAL:
Define recompensas disponibles en el sistema que pueden ser otorgadas a usuarios 
por completar objetivos. Cada recompensa tiene un costo en puntos, tipo, valor y 
requisitos asociados.

CAMPOS PRINCIPALES:
- id_recompensa (STRING UUID, PK): Identificador unico
- nombre (STRING 100): Nombre de la recompensa
- descripcion (TEXT, NULLABLE): Descripcion de la recompensa
- puntos_requeridos (INTEGER, NULLABLE): Puntos necesarios para obtenerla
- tipo (STRING 50): Tipo de recompensa (badge, descuento, acceso, etc)
- valor (INTEGER): Valor numerico de la recompensa

================================================================================
FLUJOS PRINCIPALES DEL SISTEMA
================================================================================

FLUJO DE AUTENTICACION:
1. Usuario registra: POST /api/auth/register con username, correo, password
2. Backend hashea password y crea Usuario con rol por defecto
3. Usuario login: POST /api/auth/login con credenciales
4. Backend valida y retorna JWT token
5. Frontend almacena token en localStorage
6. Cada peticion posterior incluye token en header Authorization

FLUJO DE SESION DE ESTUDIO:
1. Usuario selecciona tecnica: GET /api/tecnica
2. Usuario inicia sesion: POST /api/sesion con tecnica_id
3. Backend crea Sesion con estado "EnProgreso"
4. Usuario finaliza sesion: PUT /api/sesion/<id> con estado "Completado"
5. Backend calcula duracion_real y actualiza progreso
6. Frontend consulta progreso actualizado: GET /api/progreso/hoy

FLUJO DE SALA COLABORATIVA:
1. Usuario crea sala: POST /api/sala con datos
2. Backend asigna creador_id y genera codigo_acceso si es privada
3. Sistema agrega creador a UsuarioSala con rol "lider"
4. Otros usuarios se unen: POST /api/sala/<id>/unirse-privada
5. Sistema verifica codigo y agrega usuario a UsuarioSala
6. Usuarios visualizan participantes: GET /api/sala/<id>
7. Usuarios envian mensajes: POST /api/sala/<id>/mensajes
8. Usuarios inician sesion grupal: POST /api/sesion con es_grupal=true

FLUJO DE TAREAS:
1. Usuario crea tarea: POST /api/tarea con fecha_vencimiento
2. Backend crea Tarea con estado "Pendiente"
3. Usuario actualiza estado: PUT /api/tarea/<id> con estado "Completado"
4. Sistema registra en Progreso
5. Usuario lista tareas con filtros: GET /api/tarea?estado=Pendiente

FLUJO DE RECOMPENSAS:
1. Sistema verifica condiciones (sesiones, puntos, tareas)
2. Si se cumplen, otorga Recompensa: Crear RecompensaUsuario
3. Usuario ve recompensas: GET /api/recompensa
4. Usuario ve recompensas personales en dashboard

NOTAS DE IMPLEMENTACION
================================================================================

TOKEN JWT:
- Generado con flask-jwt-extended
- Expiracion configurada en backend
- Almacenado en localStorage del frontend
- Incluido en header Authorization: Bearer TOKEN

VALIDACIONES BACKEND:
- Email unico y formato valido (regex en validators.py)
- Password minimo 8 caracteres, mayuscula, numero (validators.py)
- UUID para IDs principales
- Foreign keys para integridad referencial
- Soft deletes para Usuario (campo activo)

MANEJO DE ERRORES:
- 400: Solicitud invalida (datos faltantes o incorrectos)
- 401: No autenticado o token expirado
- 403: No autorizado (sin permisos)
- 404: Recurso no encontrado
- 500: Error interno del servidor

INTERCEPTORES FRONTEND:
- api.jsx agrega token automaticamente a cada peticion
- Maneja 401 eliminando credenciales
- Devuelve error para que componentes manejen

ESTRUCTURA DE CARPETAS BACKEND:
app/
  models/ (16 archivos, cada uno define una tabla)
  routes/ (11 archivos de endpoints)
  controllers/ (logica de negocio)
  services/ (servicios reutilizables como RecompensaService)
  utils/ (validadores, email, etc)
  config/ (configuracion de base de datos)

ESTRUCTURA DE CARPETAS FRONTEND:
src/
  services/ (api.jsx, auth.jsx, tareas.jsx, etc - llamadas HTTP)
  pages/ (vistas completas)
  components/ (componentes reutilizables)
  IMG/ (imagenes)
  assets/ (recursos estáticos)

CONFIGURACION BASE DE DATOS:
- Motor: MySQL 8.0+
- Base de datos: synapse_db
- Usuario por defecto: root
- Migraciones: Alembic (backend/migrations/)
- ORM: SQLAlchemy con Flask-SQLAlchemy

================================================================================
CAMBIOS RECIENTES Y NOTAS IMPORTANTES
================================================================================

1. USUARIO: Se agregaron campos de perfil (nombre_completo, telefono, ubicacion, 
   fecha_nacimiento, descripcion, preferencias) para mejorar perfiles de usuarios.

2. TECNICA: Se agregó campo categoria para clasificar tecnicas por tipo 
   (meditacion, productividad, respiracion, etc).

3. SESION: Campo duracion_real registra tiempo real vs estimado. Campo estado 
   permite rastrear diferentes fases de la sesion.

4. SALA: Sistema de codigo_acceso de 6 caracteres para salas privadas. 
   max_participantes permite limitar aforo.

5. PASSWORD_RESET: Sistema de recuperacion con codigos numericos por correo, 
   válidos 15 minutos, con tabla de seguimiento.

6. ESTADO_ANIMO: Nueva tabla para rastrear bienestar emocional. Query promedia 
   valores diarios para graficos.

7. JWT: Token basado en id_usuario para todas las rutas autenticadas.

8. SOFT DELETE: Usuario usa campo activo en lugar de eliminar registros.

9. PARAMETROS SESION: Flexibilidad para diferentes configuraciones de tecnicas 
   mediante tabla SesionTecnicaParam.

10. RECOMPENSAS: Sistema gamificado con requisitos JSON para condiciones complejas.
